### 1.2 入れ物の一本化（著者が同意し、最後まで退けていない）

- `( )` は、順序のある項目の並び。各項目は名前を持つか、持たない。リストは「全部名前なし」、マップは「全部名前あり」の状態。
- 著者の言葉: 「リストとは `(0: a, 1: b, 2: c)` であると考えることは不可能なのだろうか」「`item(0)` というのは宣言時の順序で取得する関数ではないか。スキーマが無い `(a, b, c).0` は key を 0, 1, 2 に暗黙に割り当てられる、これがリストではないか」。
- 引き方は二つ: `.0` と `.key` はキーで引く。`.item(n)` は書かれた順で引く。
- 裸の整数は名前になれない（`(0: a)` は書けない）。引用符付きなら名前になれる。
- 値の位置の `{ }` は要らなくなる可能性がある（著者: 「もはや `{}` が必要ない可能性があるんだ」）。`{ }` はゲートの部品（`{$ … }` など）と、左のものに付く meta に残る。
- リストとタプルは構文で分けない。型が言う。
- 著者は後に、これをこう言い直している: 「私が納得した新構文は、リスト `[]` とマップ `{}` を合わせたタプル `()` を tomet の一級構文にすること」。

### 1.3 `name(…)` の意味（Claude が四回言い換え、著者が退けた）

Claude の案の変遷:

1. 「`name(…)` は `name: (…)` の別綴り。call は値の種類ではなくなる」。著者は、四つの書き方が「全部同じか」と確かめ、Claude は「同じ」と答えた。
2. 「`name(…)` は項目一つの入れ物 `(name: (…))` という値」。`colors: (rgb(1,2,3), rgb(4,5,6))` を通すために変えた。四つのうち一つは「別物」と訂正した。設計メモはこの形で書かれ、段階 2 の指示書もこの形で出された。
3. 「記号のない `name(` は常にキー `name: (` の省略」（著者が `::format(meta(…))` は `format.0.meta` になるのか、暗黙の了解が隠れているのではないか、と問うたのに対して）。
4. 「記号のない `name(…)` をデータから消す」（著者の「二つの書き方、要らなくね？」に対して）。

著者の判定: 「絶対におかしい」。理由は、`name()` を `name: ()` と解釈すると `(0: name())` と `(name())` の意味が変わってしまうこと。

その後の合意:

- `name(…)` は、名前の付いたタプルという独立した値（Rust の `(a, b)` と `Name(a, b)`）。キーに読み替えない。
- アクセスは著者の案: `key: name(a: b)` で `key.a == b`、頭の名前は `key::sigil == name`。Claude は呼び名を `::name` にすることを勧めた（未決）。
- 値が持つ名前と、その値が入っている場所の名前は別のもの。

Claude が後から述べた、誤読の出どころ: call を値の種類から消したかったこと。宣言の頭の規則を値に持ち込んだこと。serde の enum の書き出し方を意味の同一性と取り違えたこと。

### 1.4 評価されるものは `$`（著者が同意）

- 著者: 「`$`。この記号は木を操作する。完璧な一貫性だ」「Call のことを関数と呼んでいたのは我々だ。関数なのだから `$` はつけるべきだった」。
- 構築子（`string(…)`、`int(…)`、`float(…)`）は式の空間の関数になる。評価の仕組みが無い読み手では、これまで通り `$…` はエラー（著者: 「今まで通りで良いのでは」）。
- `$` は呼び出しごとの印ではなく、評価の空間への入口。`.$at(…)` にはならない。
- 著者の着想: `<$string> aaa`、`<$string>(aaa)` もありうる。`at(key, default:)` は、取得できなかった時の代替を設定できるので、いつか必要になる。

## 5. 見つかった事実

コード（ワークスペース `one-container`、段階 2 の前の状態で確認）:

- 要素の `( )` は三通りに化けていた: `()` は空のマップ、`(x)` は裸の値、`(x, y)` は位置の項目が空文字キーのマップ。
- 値の位置の call を評価していたのは、パーサの中の三つの構築子（`string`、`int`、`float`）だけ。型（`type: list(string)`）は call として読まれ、`enum(…)` は何もされずに運ばれていた。
- プリンタは AST だけから書く。フォーマッタと編集モデル（`tomet-edit`）は CST の上で働き、往復でバイト単位に一致する。
- `tomet refactor` は、利用者のファイル全体を AST からプリンタで書き戻している。
- 最初の質問（tomet に足りないもの）への調査で分かったこと: dev shell の twrit が古く `.writ.tmt` のルールを 0 件しか読まない。`tomet check-links` がこのリポジトリ自身で赤。`::id` から文書を引く道が無い。構造で絞り込む検索が未実装。アドレスを渡して値を読む CLI が無い。

先例（Claude の知識から。Typst 0.15 の状況だけ検索で確認）:

- 入れ物を一種類にした言語: PHP、Lua、R。括弧に位置と名前を混ぜる言語: Lisp、Typst、Swift、Dart、RON。すべてを「頭 + 引数」にした言語: Mathematica。三つを同時にやり、マップに `{ }` を使わないシリアライズ形式は見当たらなかった。
- JSON、TOML、Nix が `{ }` なのは、祖先で `( )` が式のグルーピングに取られていたから。
- 先人が痛んだ所: 空の入れ物の JSON 化（PHP、Lua）、数に見えるキーの同一視（PHP）、名前の重複（R）。
- Typst: 配列も辞書も括弧だが型は二つのまま。空の辞書は `(:)`、一要素の配列は `(1,)`。引数は位置と名前の混在。`none` と `auto` の区別。取り込みに版を書く。位置で変わる値には `context` の印が要る。HTML 出力は 0.15（2026 年 6 月）でも実験扱い。
- 属性: Rust `#[…]` `#![…]`、C++ `[[…]]`、C# `[…]`（`[assembly: …]`）、Java `@…`（引数一つなら `value` という名前に入る）、Python `@…`、PHP `#[…]`、Swift、Kotlin（`@file:…`）。AsciiDoc は文書の先頭に `:name: value`、ブロックの前の行に `[…]`、ブロックのマクロは `name::target[…]`。
