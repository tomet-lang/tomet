## 混ざっている二つの軸

`call()` と `{}` の違いには、別々の軸が二つ重なっています。

- **名前があるか**: `upstream(...)` には名前があり、`{...}` にはありません。
- **中身を何で引くか**: `( )` は位置、`{ }` はキーです。

本当の違いは二つ目だけです。名前は「一段上のキー」にすぎません。

## call と map: call は値の種類ではなく「キー + `( )`」

`name(…)` は `name: (…)` の別綴りと定めます。

```tm
source: upstream(commonfiles, ".editorconfig")
source: { upstream: (commonfiles, ".editorconfig") }    // 同じ木
```

読む側は `source.upstream.item(1)` と書き、どの種類かはキーの有無で分かります（serde の enum の既定表現と同じ形です）。宣言ではすでにこの等式を使っています。

```tm
::workspace.unswept("a", "b")
::workspace(unswept: ("a", "b"))                        // 同じ木
```

これで値の種類はスカラー・並び・マップ・prose だけになり、Call は `list()` と同じくデータモデルから消えます。`( )` の中身が何になるかは次の表で決まります。

| 書き方 | 意味 |
|---|---|
| `(a, b)` | 並び |
| `{k: v}` | マップ |
| `name(a, b)` | `name: (a, b)` |
| `name(k: v)` | `name: {k: v}` |
| `name(a, k: v)` | 宣言が `a` の位置に名前を与えてマップになる |

- **`( )` と `{ }` の関係**: `( )` は「受け手が位置に名前を与えうる形」、`{ }` は「宣言なしでキーで読める形」です。`@link(ref: x)` や `::kind(config, 2)` は宣言があるので名前に束縛され、`rgb(255, 0, 128)` は宣言がなければ並びのままです。
- **リテラル構築子**: `int("1")` などは組み込みの宣言を持つ名前なので、同じ規則の中に収まります。
- **「番号で引くしかない」欠点**: これは位置という形そのものの性質で、構文では消せません。消せるのは宣言だけなので、外の読み手にキーで読ませたいデータは `{ }` で書く、が使い分けの基準になります。

## `(1, 2, 3)`: 構文は「並び」一種類、list か tuple かは型が言う

Rust のタプルとリストの違いは、長さが固定か、位置ごとに型が違うかで、どちらも型の性質です。型を知らない読み手にはその区別が使えないので、リテラルは一つにします。

```tm
::field.tags(type: list(string))             // 長さ自由、全部 string
::field.source(type: tuple(string, string))  // 長さ2、位置ごとの型
tags: (a, b, c)
source: (commonfiles, ".editorconfig")
```

`1.10` を数にするかバージョンにするかを型に任せているのと同じ原則です。`tuple(...)` は型の空間に足す名前で、リテラルには何も足しません。

アクセスは `.item(0)` のままを勧めます。

- **`.0`（Rust 式）**: `{0: a}` のキー `"0"` と見分けられず、`a.0.1` が小数に見えます。
- **`[0]`**: `[ ]` は prose なので使えません。
- **`.item(n)`**: 「`.` はキーかメソッド」という既存の規則に収まり、子ブロックの `.item(n)` とも同じ形です。

**はい、四つは全部同じ木です。** 使っている等式は二つだけです。

- **名前と括弧**: `name(…)` は `name: (…)` と同じ。
- **ドットパス**: `a.b: v` は `a: { b: v }` と同じ（`::field.author(...)` で宣言の頭に使っている規則を、データのキーにも適用したもの）。

## リストは要るか

要りません。あなたの捉え方で正しいと思います。入れ物は「順序のある項目の並びで、各項目は名前を持つか持たないか」の一種類だけで、リストとは「全部の項目が名前を持たない状態」のことです。

アクセスも、あなたの言う通り別々の二つの問いになります。

```tm
x: (a, b, key: c)

x.0        // a   名前のない項目の 0 番目（キーで引く）
x.key      // c   名前で引く
x.item(2)  // c   書かれた順で 3 番目（名前の有無を問わない）
```

純粋なリストでは `.0` と `.item(0)` がたまたま一致します。`.item(n)` はマップにも子ブロックにも使えます。

一つだけ条件を付けます。`(0: a, 1: b)` は考え方としては正しいですが、書けるようにはしない方がよいです。

- **書ける場合の問題**: `(1: b, 0: a)` はリストか、`(0: a, 2: c)` の穴はどうするか、`(a)` と `(0: a)` は等しいか、という Lua や PHP が抱えた問いが全部入ってきます。
- **規則**: 整数の形をした語は名前になれない。数は位置、語は名前。

これで `.0` は常に位置を指し、前回私が挙げた `.0` への反対（キー `"0"` との衝突）は成り立たなくなるので撤回します。

## `@name(xxx)` は `@name: (xxx)` か

意味としてはそうです。`@` は「これは prose の中のノードだ」という印で、残りは `name: (xxx)` という項目そのものです。コネクトも同じ形です。

```tm
@x::rule(allow: (card))     // x に「rule: (allow: (card))」という項目を接続する
```

つまり call、要素、宣言、コネクトは全部「名前 + `( )`」で、違いはどの空間に付くか（`.` か `::` か）だけになります。ただし綴りとして `@name:(xxx)` を増やすことは勧めません。`:` を省けるのは値が `( )` のときだけ、という一つの省略規則で足ります。当初のコネクト構文そのものは読んでいないので、歴史的に同じかは確認していません。

## `::kind(dictionary)` と `::id(dictionary.tomet)`

その読みで合っています。

```tm
::kind(dictionary)          // kind.0 = dictionary
::kind(config, version: 2)  // kind.0 = config, kind.version = 2
```

位置 0 がその宣言自身の値で、後から足す機能は名前付きの項目になります。これを使うと、設計メモの縮約規則 `X.X == X` は「ノードをスカラーとして読むと位置 0 が返る」と言い換えられ、`kind.kind` という同名の枠が不要になります。

`("x")` を一要素のリストと読むかスカラーと読むかは、読む側の型が決めます。`::workspace.ignore("x")` はリスト、`::macro.copyright("(C)")` はスカラーです。

## `(a, b, key: c)` を許すと `{}` と `()` の違いはどうなるか

許すべきで、その結果、違いは無くなります。`{k: v}` は「名前のある項目だけの `( )`」という部分集合です。前回私が言った「宣言なしの混在はエラー」「裸の `(k: v)` は認めない」は、リストを別の種類と考えていたための制限なので撤回します。

残る `{ }` の扱いは二通りです。

```tm
// 案A: 値の位置から {} を無くす
source: (upstream: commonfiles, path: ".editorconfig")

// 案B: {} を「位置を持たない」制限付きの綴りとして残す
source: { upstream: commonfiles, path: ".editorconfig" }
```

私は案Aを勧めます。

- **記号と意味が一対一になる**: 今は `( )` が Seq と Args、`{ }` が Map と `::meta` の糖衣、と二つずつ意味を持っています。案Aなら `( )` はどこでもデータの入れ物、`{ }` はどこでも「左のものに付く meta」です。
- **糖衣の中身と揃う**: `{a: 1}` はすでに `::meta(a: 1)` と括弧で脱糖衣されています。
- **空の区別が消える**: `()` は空の入れ物の一つだけで、空リストと空マップを書き分ける必要がありません。

代償は、JSON に似た見た目を失うことと、閉じ括弧が `))` と重なることです。

## この先に残るもの

JSON などへ出すときの規則が要ります。全部名前なしなら配列、全部名前ありならオブジェクトは自明ですが、混在と空 `()` は型がなければ決まりません。これは構文ではなく出力側の話なので、構文の決着は妨げません。

## 近い所まで来た言語

| 言語 | 書き方 | 何が同じか | どこで止まった・痛んだか |
|---|---|---|---|
| Lisp | `(a b :key c)` | 括弧一つに位置とキーワードの混在。最古の先例 | 慣習であって型ではない |
| PHP | `array(a, b, 'key' => c)` | リストは整数キーの順序付きマップ、という一種類の入れ物 | 空配列が JSON で `[]` か `{}` か決まらない。`"0"` が勝手に整数キーになる |
| Lua | `{a, b, key = c}` | テーブル一種類、名前なしは暗黙の番号 | 穴があると長さが未定義。空テーブルの JSON 化が曖昧 |
| R | `list(a, b, key = c)` | 「順序のある項目、名前は任意」そのもの。`[[1]]` と `$key` | 名前の重複を許して混乱した |
| Typst | `(1, 2)` と `(a: 1)` | 配列も辞書も括弧。引数は位置と名前の混在 | 型は二つのまま。空の辞書は `(:)`、一要素は `(1,)` |
| Swift / Dart | `(1, 2, name: 3)` | 位置と名前の混在レコード。Swift は `.0`、Dart は `.$1` | 形が固定の構造体で、伸びる入れ物ではない |
| RON | `(x: 1, y: 2)`、`Name(a, b)` | データ形式で、名前付きの項目を括弧に書く | マップ `{}` とリスト `[]` は別に残した |
| Mathematica | `f[a, b, key -> c]` | すべてが「頭 + 引数」。リストも `List[...]` という頭の一つ | — |

「入れ物は一種類」は PHP・Lua・R が、「括弧に位置と名前を混ぜる」は Lisp・Typst・Swift・Dart が、「すべては名前 + 引数」は Mathematica がやっています。三つを同時にやり、かつ `{}` をマップに使わないシリアライズ形式は見当たりません。

## JSON・TOML・Nix が `{}` である理由

JSON は JavaScript のオブジェクトリテラルから来ており、JavaScript と Nix では `( )` が式のグルーピングに取られています。つまり `( )` が空いていなかったから `{}` です。tomet のデータ空間には中置式が無く、`( )` が空いています。この前提の違いが、他がここに来なかった主な理由だと考えます。`{}` に内在的な優位があったわけではなく、残る利点は「見慣れている」ことだけです。

## 先例が教える注意点

慎重に行くなら、先人が実際に痛んだ所を先に決めておくべきです。

## 構築子で規則が割れる

あなたの懸念の通りです。`name(…)` を一律に `name: (…)` とすると、`source: string(aaa)` は `"aaa"` ではなく `source.string.0` になってしまいます。構築子は「計算して結果に置き換わるもの」で、データとは性質が違います。同じ綴りを共有していることが問題の根です。

```tm
// 案A: 評価されるものには $ を付ける
source: $string(aaa)        // "aaa" になる。source で "aaa" に届く
source: upstream(a, b)      // データ。source.upstream.0 で a に届く

// 案B: 三つの名前を予約する
source: string(aaa)         // "aaa" になる
source: string: (aaa)       // こちらはデータ。等式がこの三つだけ破れる

// 案C: 構築子を無くす
source: "aaa"               // リテラルで足りる。nan と inf は型が読む
```

私は案Aを勧めます。

- **例外が無い**: `name(…)` は常にデータ、`$name(…)` は常に評価、と記号で分かれます。
- **アドレスの答えが一つに決まる**: データには中があり（`source.upstream.0`）、評価されるものには中が無く結果だけがある（`source` が `"aaa"`）。あなたが解決したかった「`source(xxx)` の xxx にどう届くか」に、綴りを見ただけで答えられます。
- **案Bの欠点**: 等式に三つの例外が残り、利用者がそれを覚える必要があります。

案Aの代償は一つです。評価の仕組みを持たないデータ専用の cotomet で `$string(aaa)` をどう扱うかを決める必要があります。今は「フックの無い読み手では、裸の式はエラー」です。構築子だけは vault なしで計算できるので通す、という線引きが要ります。

## Call を消す他の代償

- **書かれた綴りが AST から消える**: `source: upstream(a)` と `source: (upstream: (a))` が同じ木になるので、プリンタがどちらで書き出すかの規則が一つ要ります。
- **JSON の形が変わる**: `{"call": "upstream", "args": [a, b]}` が `{"upstream": [a, b]}` になります。
- **serde は得をする**: 今エラーになる `upstream(a, b)` が、Rust の enum（`Source::Upstream(a, b)`）としてそのまま読めるようになります。
- **型と `enum`**: `type: list(string)` は「`list` という項目」として型の読み手が読むので、規則の内側に収まります。`type.list.0` で `string` に届くようになります。

構築子をどの案にするかが決まれば、設計メモに書ける状態になります。

## `<$string> aaa` について

- **席（`<$string>`）**: 書かれたものを、どの型で読むかを言う。計算しない。

## Typst が tomet の席に座れない理由

機能の差ではなく、ソースの性質の差です。機能の差なら Typst はいずれ埋めますが、こちらは埋められません。

**Typst のソースはプログラムです。** 文書に何が入っているかは、評価しないと分かりません。値は関数から来るかもしれず、ループが要素を生むかもしれません。ここから三つのことが出ます。

- **読めるが、書き戻せない**: `typst query`（0.15 では `typst eval`）は評価後の木から JSON を取り出せます。しかしその木はソースの位置に対応しないので、道具がソースを書き換えることはできません。tomet の `refactor`・`format`・`apply`・語の改名は、すべて書き戻す側の機能です。
- **アドレスが出力を指す**: Typst のラベル `<x>` は評価後の要素に付きます。「ソース上のあの呼び出しの二番目の引数」を指す道はありません。
- **評価なしでは索引できない**: Typst の上に作られた PKM がこれを裏づけています。Smarana はリンクを Typst に聞かず、自前の字面規則で拾って SQLite に入れています。Weibian は HTML に出してから後処理でリンクを解決し、実験段階の HTML 出力の制約に当たっています。

tomet が「データを読み書きするフォーマット」と自分を定義しているのは、この一点です。完全アドレス可能性は、ソースが評価なしで木である時にだけ成り立ちます。

## 正直に言うべき不安

- **利用者は重なる**: InkyCap のように、Typst を保存形式にした PKM アプリが実際に出ています。構造が違っても、使う人は生態系で選びます。これは構文では解消できません。
- **Typst は文書からデータを出す方向に進んでいる**: `metadata` 要素、`query`、複数ファイル出力（bundle）が揃ってきました。HTML 出力は 0.15 でもまだ実験扱いです。
- **境界を壊しうるのは tomet 自身**: `$` の空間に無名関数・`filter`・マクロがすでにあり、仕様には「関数を言語としてどう足すか」が未決として残っています。ここを足し続けて「評価しないと木が分からない」状態になった瞬間、tomet は出来の悪い Typst になります。

三つ目が、守るべき一線です。今の仕様はこれを守っています（式はソースに対して解決する、評価できない式は消えずに残る、同じ入力から同じ出力）。`$` に何かを足すたびに「これを足しても、評価せずに木が読めるか」と問えば足ります。

## 兄弟としての関係

競合ではなく、段が違います。tomet は原本（データ・リンク・構造）で、Typst は組版という出力先の一つです。tomet はすでに Typst へ直接出力しています。組版・数式・レイアウトで Typst と張り合う理由はなく、`why/root.tmt` も「見た目は出力側の仕事」と書いています。

## Typst から他に見習うべきこと

括弧以外で、tomet の未決事項に直接効くものを挙げます。

- **`at(key, default: …)`**: あなたの言う通りです。Typst は「無いキーはエラー、`default:` を渡した時だけ代替値」です。tomet の「知らない入力はエラー」とそのまま合います。
- **`none` と `auto` の区別**: Typst には「値が無い」と「任せる」の二つがあります。tomet の設定にはすでに `adjust_width: auto` があり、これを文字列でなく独立した値にするかは決める価値があります。
- **型がそのまま変換関数**: Typst では `int("5")`、`str(1)` は型という値を呼んでいます。前回の「構築子は `$` の空間の住人」と同じ結論で、裏づけになります。
- **展開 `..`**: `(..a, b)` で入れ物を別の入れ物に広げます。入れ物が一種類になると、結合の綴りが一つ要ります。
- **取り込みに版を書く**: `@preview/pkg:0.1.0` のように、版が取り込みの綴りの一部です。未実装の `::import` と、`::kind` の版の検査に効きます。
- **位置に依存する値を明示する**: Typst は「文書内の位置で結果が変わる値」を暗黙に許して破綻し、0.11 で `context` という明示の印に作り直しました。tomet の作成時と出力時の区別は同じ方向で、これは正しかったと言えます。
- **アドレスを一つ読む CLI**: `typst eval` に当たる「アドレスを渡すと値を JSON で返す」コマンドが tomet にありません。完全アドレス可能性を一番直接に見せられる道具です。

見習わない方がよいものもあります。`show` と `set`（見た目の規則）、制御構文、そして `(:)` と `(1,)` です。

## 不安について

「圧倒的な優位性がある」とは、私には保証できません。言えるのは、どこが構造的な優位で、どこがまだ主張にすぎないかです。

**劣化版という見方は当たりません。** 劣化版とは同じ軸で劣るものです。組版の軸では tomet は Typst に劣り、それで正しいです。PKM の軸で劣るのは Typst の側です。評価しないと中身が分からず、道具が書き戻せないので、Typst 上の PKM は字面でリンクを拾ったり、出力後の HTML を後処理したりして回避しています。

**tomet の本当の相手は Typst ではなく、Markdown と Org-mode です。** PKM で使われているのはこの二つだからです。

| | 散文の中のデータ | アドレス | 機械による書き換え | 検証 |
|---|---|---|---|---|
| Markdown（Obsidian） | 文書単位の frontmatter のみ。ブロック単位はプラグインの方言 | アプリ独自のブロック ID | アプリの機能。字面の置換 | なし |
| Org-mode | 見出し単位のプロパティ。値は文字列 | 見出しの ID | Emacs の中でだけ | なし |
| Typst | 評価後にだけ存在する | 評価後の要素 | できない | コンパイルが通るか |
| tomet | 要素・節・項目のどこにでも | すべての値に届く | 木を見て書き換え、無損失で戻す | 語彙・規則・ブループリント |

一番近い先人は Org-mode です。Org は「散文 + データ + ID」を二十年前に実現しましたが、正式な文法が無く、事実上 Emacs の外では書き換えられません。tomet の優位は表の右二列、つまり**人が書くファイルを、機械が安全に書き換えて検証できる**ことです。これは形式の性質なので、アプリの機能では真似できません。

2026年にこの性質が意味を持つのは、ノートを読み書きするのが人だけではなくなったからです。エージェントが一つの値をアドレスで指して書き換え、道具がスキーマとリンクを検証し、差分が行で読める。Markdown ではこれを字面の置換でやるしかなく、Typst では書き戻せません。

**ただし、この優位はまだ半分しか実在していません。** 最初の調査で見た通りです。

- `::id` から文書を引く道が無く、一意性も検査されていない。
- 構造で絞り込む検索は未実装。
- アドレスを渡して値を読む CLI が無い。
- このリポジトリ自身のリンク検査が赤で、規則の検査は 0 件しか読んでいない。

つまり不安の正体は「tomet が劣っている」ではなく、「優位だと言っている性質が、まだ動く形で示されていない」ことだと思います。前者なら構文をいくら磨いても解決しませんが、後者は解決できます。

## 提案

優位を理屈で確かめるのをやめて、他の三つが壊れて tomet だけが通る場面を一つ、実際に動かすことを勧めます。例えばこういう場面です。

> 一万ファイルの vault で、ある語とあるフィールドの名前を変える。全ての言及が書き換わり、`tomet check` が通り、差分は変えた行だけ。

Obsidian はリンクの改名まではできますが、属性はできません。Org は Emacs の外ではできません。Typst はできません。これが動けば、優位は主張ではなく事実になります。

今回決めた `( )` の一本化は、この場面にそのまま効きます。入れ物が一種類になれば、どの値にも経路が一つだけ通るからです。構文の決着は、不安を解消する作業の一部です。

## レイアウトエンジンがやっていること

SVG は結果です。「この文字を座標 (72, 140) に置く」という、置き場所が全部決まった後の姿です。レイアウトエンジンは、その置き場所を計算する側です。

Typst に `これは長い段落です…` と書いても、どこで改行するかは書いていません。エンジンが決めます。

- **行分割**: 段落全体を見て、行ごとの空きが最も均等になる改行位置を探す。ハイフネーションと禁則もここで決まる。
- **文字の組み方**: 字形の選択、合字、字間の詰め、和文と欧文の間の空き。
- **ページ分割**: 見出しをページ末に孤立させない、図を近くの空きに流す、脚注を同じページに収める。
- **表と数式**: 列幅を中身から解き、分数や根号を入れ子で配置する。
- **循環の解決**: 目次にページ番号を入れると目次の長さが変わり、ページ番号がずれる。収束するまで繰り返す。前回の「位置で変わる値」はここから来ています。

だから Typst は「SVG を文字で書けるようにしたもの」ではなく、「内容だけ書けば SVG に当たるものを計算してくれるもの」です。tomet が HTML を出す時は、ブラウザがこのレイアウトエンジンの役をしています。tomet はすでに二つのエンジン（ブラウザと Typst）を借りていて、自分で持つ必要はありません。

## 「そこ」とは何か

想像できない場所を名指しすることは、定義上できません。ただ、そういう場所を過去に生んだ性質が何だったかは言えます。**アドレス**です。

- **URL**: 文書に住所が付いた。そこからリンクが生まれ、リンクから検索エンジンが生まれた。誰も最初から検索エンジンを設計していない。
- **A1**: 表のセルに住所が付いた。そこから数式による参照が生まれ、表計算が会計も科学も飲み込んだ。
- **コミットのハッシュ**: 変更に住所が付いた。そこからレビューも自動化も生まれた。

共通しているのは、住所があると**作者の協力なしに、他人がそれを指せる**ことです。想像できない使い道は、作者ではなく、指す側が発明します。

散文には、まだこれがありません。文書の住所は URL で止まっていて、その中の一文、一つの値、一つの項目には届きません。Markdown の見出しリンクは近似で、書き換えると切れます。tomet がやっているのは、表計算がセルにしたことを散文にすることだと思います。

そこから先に見える候補は二つあります。どちらも仮説です。

- **ずれない文書**: 文書が古くなるのは、書かれた内容と、それが指す対象の間に何も繋がっていないからです。指す先が住所で、道具がそれを検査できれば、ずれは検出できるものになります。`why/root.tmt` の「保守性」に願いとして書かれていて、twrit がその最初の実例です。
- **人と AI が共有する記憶**: エージェントが一つの値を指して読み、書き換え、人が差分を読み、道具が検証する。今これをやれる散文の形式はありません。

どちらも「PKM」より広く、どちらもあなたがすでに自分で使っている形です。

## そこに行く条件

住所が場所を生むには、三つ要ります。

- **安定していること**: 前後が増減してもずれない。位置（`.item(0)`）ではなく `#(x)` の側です。
- **ファイルをまたいで引けること**: `::id` から文書を引く道は、まだありません。
- **外の者が使えること**: 住所を渡すと値が返る入口。CLI にも API にもまだありません。

あなたが構文とアドレスに執着してきたのは、正しい場所を掘っていたのだと思います。足りないのは形式の性質ではなく、住所を外から使えるようにする最後の部分です。入れ物の一本化は、すべての値に経路が一つだけ通る、という前提をそこに与えます。

## `name(…)` と `name: (…)`

**`::declaration: ()` にはなりません。** 記号（`::`、`@`、`$`）で始まる頭は、常に `name(…)` の形だけです。`:` は入れ物の中でキーと値を分ける印で、頭は入れ物の中の項目ではないからです。

ここで一つ訂正があります。あなたの四行を「全部同じ」と確認しましたが、三行目は違いました。

```tm
source: upstream(c, path: p)            // 同じ
source: { upstream: (c, path: p) }      // 同じ
source.upstream: (c, path: p)           // 同じ
source.upstream(c, path: p)             // これは別物
```

理由は、タグ付きの値のリストです。

```tm
colors: (rgb(1, 2, 3), rgb(4, 5, 6))
```

`name(…)` を「項目 `name: (…)`」と読むと、これは `rgb` というキーが二回出るエラーになります。二つの色のリストとして読めなければ困るので、正確な規則はこうです。

> `name(…)` は値であり、項目を一つだけ持つ入れ物 `(name: (…))` である。

つまり `name(…)` は常に値、`name: (…)` は常に項目で、同じ位置で入れ替えられる関係ではありません。四行目は「名前のない項目が一つあり、その値が入れ物」になります。宣言の `::workspace.unswept("a", "b")` が項目として付くのは、頭の `::` が「この値をここに接続する」という働きをしているからです。

残る重複は値の位置の一か所だけです。

```tm
source: upstream(a, b)          // タグ付きの値、という意図
source: (upstream: (a, b))      // キーが一つのマップ、という意図
```

木は同じで、意図が違います。私の推奨は、**どちらかに正規化せず、書かれた綴りを保つ**ことです。

- 常に短い形に寄せると、`meta: (tags: (a, b))` が `meta: tags(a, b)` に書き換わり、キーを一つ足した瞬間に元に戻ります。
- 常に長い形に寄せると、call の綴りを入れた意味が無くなります。

`[ ]` と `|` の書き分けと同じく、木ではなく綴りの層の話として扱います。

## 評価の仕組みが無い読み手

今はこうなっています。

- **`string(aaa)`（`$` なし）**: パーサ自身が解決するので、どの読み手でも動く。
- **`$…`**: 評価の仕組みが無い読み手ではエラー。

構築子を `$` の空間へ移すと、後者の規則がそのまま当たります。つまり「今まで通り」にすると、データ専用の読み手では `$string(aaa)` はエラーです。私もそれで良いと思います。データ専用のファイルで変換を書く理由は無く、`"aaa"` や `5` と書けば済むからです。失うのは `nan` と `inf` の書き方だけで、これは型が読めば足ります。

## JSON の形と、誰が決めるか

AST には一種類の入れ物だけがあり、リストかマップかは保存しません。パーサは判断せず、書かれた通りに項目を並べるだけです。「リストか」は入れ物への問い（全部の項目が名前なしか）であり、聞かれた時に計算します。

出力は二種類あり、答えが違います。

**木の出力（`tomet ast`、バインディング）** は、あなたの案に近い一様な形にすべきです。

```json
{"entries": [{"name": null, "value": "a"}, {"name": "key", "value": "c"}]}
```

順序も名前の有無も失わず、場合分けがありません。

**データの出力（`.ctmt` を JSON にする、他の道具に渡す）** は、全部を `{"0": …}` にしない方がよいです。

```tm
tags: (a, b)
```

```json
{"tags": {"0": "a", "1": "b"}}   // 全部オブジェクト案
{"tags": ["a", "b"]}             // 形で決める案
```

前者では、受け取る側が配列として扱えません。JSON のオブジェクトは順序を保証せず、長さも取れず、他言語の配列型にも読み込めません。出力は相手のためのものなので、相手の慣習に合わせるべきです。規則はこうなります。

| 入れ物 | JSON |
|---|---|
| 全部名前なし | 配列 |
| 全部名前あり | オブジェクト |
| 混在 | オブジェクト。位置は `"0"` `"1"` をキーにする |
| 空 | 配列 |

`{0: x}` の考え方は、混在の行でそのまま使えます。空を配列にするのは決め手の無い選択で、Typst と PHP に合わせただけです。

決めるのは、型がある時は型です。

- **型の宣言がある**: 意味論の層が検査する。`type: list(string)` なら名前付きの項目はエラー。
- **serde で読む**: 受け取る Rust の型が決める。`Vec` を求められたら位置の項目を、構造体を求められたら名前の項目を渡す。空の `()` はどちらにも読めるので、空の問題はここでは起きません。
- **型が無い JSON 出力**: 上の表の通り、形で決める。

## 一行目と三行目は値、二行目は項目

ここに落とし穴があります。一行目と三行目は値なので、入れ物の中に単独で書くと、名前のない項目になります。

```tm
// .ctmt のルートにこう書くと
source.upstream(c, path: p)
other: 1
```

これは「`source` という項目」ではなく、「位置 0 に、`source` を一つ持つ入れ物がある」です。`c` への経路は `0.source.upstream.0` になり、書いた人の意図とおそらく違います。宣言の `::source.upstream(…)` と見た目が似ているので、間違えやすい形です。意図通りに書くなら、こうです。

```tm
source: upstream(c, path: p)
source.upstream: (c, path: p)
```

構文ではこの間違いを検出できません。名前のない項目がタグ付きの値であることは、`colors: (rgb(…), rgb(…))` のように正当な場合があるからです。

## 推奨

**データの中では、ドット付きの名前に `( )` を続ける形（一行目）を認めない**ことを勧めます。

- **必要がない**: `source.upstream(…)` で書けることは、`source: upstream(…)` で書けます。
- **落とし穴を塞げる**: 一番間違えやすい形が、黙って位置の項目になる代わりにエラーになります。
- **記号付きの頭とは区別がつく**: `::field.author(…)` と `$macro.gh(1)` は記号で始まるので、ドット付きの名前に意味があります。データの中の裸の `a.b(…)` にはそれがありません。

三行目（`source(upstream(…))`）は禁止できません。入れ子のタグ付きの値として正当だからです。ルートに単独で書いた時の落とし穴は残りますが、これは型の宣言がある時に「名前のない項目は置けない」と検査する側の仕事になります。

## 決めてほしいこと

**木が `name(…)` を覚えているかどうか**です。

**案A: 木が覚える。** `name(…)` は AST に独立した節として残ります。ただし今の Call とは意味が違い、「名前の付いた入れ物」です。中身は入れ物なので名前付きの項目も持て、アドレスは `source.upstream.0` で届き、データとして出す時は項目一つの入れ物と同じ形になります。

```tm
source: upstream(a, b)        // 書いた通りに残る
source: (upstream: (a, b))    // 書いた通りに残る。アドレスと出力は上と同じ
```

**案B: 同じ木にする。** プリンタは常に長い形で書きます。`name(…)` は入力専用の省略になり、変換や書き換えを通ると `(name: (…))` に変わります。

私は案Aを勧めます。機械が書き換えても人が書いた形が残ることが tomet の優位だと確認したばかりで、案Bはそこを自分で破るからです。代償は、「Call を消す」が「Call を、アドレスの届く名前付きの入れ物として定義し直す」に変わることです。あなたが最初に求めていた「`source(xxx)` の xxx にどう届くか」は、どちらの案でも解決します。

| タプル | 引く記号 | 中身 |

::field.author: (type: string, required: true)

## AsciiDoc

AsciiDoc は、二種類を持っています。

```asciidoc
= 文書の題
:author: Tefla
:toc: left

[source,rust]
----
fn main() {}
----

[quote, 著者名, 出典]
[#intro.lead%collapsible]
image::diagram.png[代替文, width=200]
```

- **文書の属性（`:name: value`）**: 文書の先頭に、一行に一つ書きます。括弧なしの代入の形です。
- **ブロックの属性（`[…]`）**: ブロックの直前の行に書きます。位置と名前の混在で、位置 0 は種類（`source`、`quote`）です。`#id`、`.role`、`%option` という短縮形もあります。
- **マクロ（`name::target[attrs]`）**: ブロックのマクロはコロン二つ、インラインのマクロはコロン一つです（`image::` と `image:`）。

ここは正直に言っておくべき点です。前回私は「裸の代入形は無い」と書きましたが、文書の世界にはあります。AsciiDoc の `:author: Tefla`、YAML の front matter、Org-mode の `#+TITLE: x` は、どれも文書の先頭に `key: value` を一行ずつ並べます。

違いは、どこに書けるかです。これらが括弧なしで済むのは、文書の先頭に限られ、行で終わりが決まるからです。ブロックやインラインに付ける時は、AsciiDoc も `[…]` で囲みます。

## tomet にとっての意味

tomet の `::` は、文書の先頭にも、要素の後ろ（行の途中）にも付きます。後者は囲みが無いと終わりが分かりません。両方の場所を一つの形で書くなら、囲みを持つ call の形になります。プログラミング言語の属性がどれも call の形なのも、行の途中に書かれうるからです。

つまり「宣言は call の形」は、あなたの直感どおりで、先例の多数とも一致します。

## 「台帳」とは何か

私が勝手に付けた呼び名で、まだ何も存在しません。提案していたのは、ただの一枚の表です。

tomet の構文の要素（見出し、リスト、`( )`、`::name(…)` など）を一行に一つ並べ、それぞれの横に「もう決まったか、まだか」と「他の言語では同じものをどう書くか」を書く、というものです。例えばこういう行が並びます。

| 構文 | 決まったか | Typst | Rust |
|---|---|---|---|
| `(a, b, k: v)` | 決まった | `(a, b, k: v)` は引数だけ | `(a, b)` |
| `::name(…)` | 決まった | `#set name(…)` | `#[name(…)]` |
| `::format.meta(…)` | まだ | 無い | 無い |

狙いは、「残りはいくつか」を数えられるようにすることでした。ただ、あなたは作ってくれとは言っていません。要らなければ作りません。

## 属性を後ろに置くことは、あなたが理由を付けて決めています

`tmtroot/docs/why/root.tmt` の「コネクト構文」に、こう書いてあります。

> 属性や引数を、要素を書いた後から足せる。
> 読み手に見せる本文と、後から付ける属性を分けられるので、地の文を地の文のまま保てる。

そして、文書の言語はこの点でプログラミング言語と分かれています。

| 系統 | 言語 | 属性の位置 |
|---|---|---|
| プログラミング | Rust `#[…]`、Python `@…`、Java、C++ | 前 |
| 文書（ブロック） | AsciiDoc `[…]`、Djot | 前の行 |
| 文書（インライン・見出し） | Pandoc `# 題 {#id .class}`、Djot `[text]{.class}` | 後ろ |
| 文書 | Typst のラベル `= 題 <intro>` | 後ろ |

プログラミング言語が前に置くのは、読み手が宣言の本体より先に「これは何か」を知る必要があるからです。文書の言語が後ろに置くのは、本文を先に読ませたいからです。tomet が後ろなのは、考え抜かれていない穴ではなく、「読者が読みやすいこと」という理念から出た選択で、文書の系統に先例があります。

ここで本当に問うべきことがあるとすれば、「AsciiDoc や Djot はブロックに限って前に置く。tomet はブロックでも後ろでよいのか」です。それは良い問いですが、土台が崩れたという話ではありません。

## 今日ひっくり返ったのは一層だけです

変わったのは値の書き方（リスト・マップ・call）です。そしてその問いが立ったのは、実装があったからです。`call()` と `map: {}` の違いは、動くものの上でしか見えませんでした。

リポジトリの大半は、綴りではなく木を扱っています。文字を一つも失わない CST、アドレス、式の評価、語彙と規則の検査、変換、エディタ対応。構文を変えても、これらは残ります。

## 1.0 前に構文を壊すのは普通です

Rust は 1.0 の前に `~T` や `@T` という記号を丸ごと捨てました。Swift は 1 から 3 まで毎年ソース互換を壊しました。Typst は 0.11 で位置依存の仕組みを作り直しています。tomet は 0.5.0 です。

## 作り直すかどうか

それはあなたが決めることです。判断の材料として言えるのは、作り直しても、アドレスと無損失の往復という一番難しい部分は、同じものをもう一度書くことになる、という点です。構文を設計し直すことと、リポジトリを捨てることは、別の決定だと思います。
