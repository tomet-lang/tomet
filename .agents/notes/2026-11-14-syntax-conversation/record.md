### 1.2 前日の残課題の整理と `{}` / 型席の扱い（発言 5〜6）

前日（`2026-11-13`）の対話で未決だった項目を洗い出し、著者が以下を判断した（発言 6）：

1. **`::path(...)` を「パス束縛」と解釈する案の却下**:
   パス束縛なら `::path:()` になるはずであり、構文が `::name()` である以上、それは `::` + 名前付きタプル（named tuple）である。
2. **`{}`（後置 `::meta(...)` 糖衣）の維持**:
   値の位置から `{}` を撤去したため、通常の `{}` は衝突が一切ない。要素・見出し・リスト項目に対する `::meta(...)` の後置糖衣としてそのまま残す。
3. **型席（type seat）の保留**:
   今すぐ決める必要はない。将来必要になれば `<$version> 1.10` のような形になる。

### 1.3 宣言ヘッドのドット廃止と複数宣言のマージ（発言 7〜8）

- 重複キーはデフォルトでエラーとし、将来優先度機能を入れるなら Nix の `lib.mkForce` のような仕組みにする方針が示された（発言 7）。
- タプル内部のキーにおけるドット記法（`url.wiki: (...)` → `url: (wiki: (...))` の糖衣）は、可読性のため維持し、ドットそのものをキー名にしたい場合は `"url.wiki"` とクォートする（発言 8）。
- `.vocabulary.tmt` 自身のヘッダは、1 ファイルに 1 つだけ自身の語彙名を宣言するもの（`::kind` や `::id`、`::dictionary(tomet)` と同類）なので位置引数 `::vocabulary(writ, version: "1.0.0")`（またはオブジェクト形式）とし、`vault.config.tmt` 側は複数語彙を登録するためキー形式にするのが自然であると整理された（発言 8）。

### 1.4 `::use(...)` と「値に属性を持たせること」「マージの一貫性」（発言 9〜13）

- 著者が `::use(a, b, c)` の問題を提起（発言 9）：
  - `::use` を複数回書いたときだけリスト結合になり、他の `::declar` はキーマージになるような「マージ方法が違う構造」は**癌になるため絶対に避けなければならない**。
  - また、`::use(a, b, c)` の `a` は単なる死んだスカラーではなく、`version: 3` のような属性を持ちうるオブジェクトである。
- エージェントが `::use(a: (version: 3), b: ())`（対象名をキーにする案）を出したところ、著者から**「`key` は辿るためのものであって、意味（値そのもの）を含んじゃ駄目」**と明確に却下された（発言 12）。
- エージェントが `::use(a{version: 3}, b)`（後置 `{}` を使う案）を出したところ、著者から**「`{}` は `meta` フィールドであって、`version` のような必須・構造プロパティを入れる場所ではない」**と却下された（発言 13）。

### 1.5 `key: object(...)` と `{}` / `()` 逆転案の検討と反証（発言 14〜17）

- 著者が思考実験として「`{key: value, key: object(key: value)}` の形にして、`{}` 内は `.` アクセス、`object()` 内は `::` アクセスにするのはどうか」と問いかけた（発言 14〜15）。
- エージェントが一度これに迎合して肯定的な整理を出したところ、著者から「本当にこれに穴ない？今、偏見で言っているでしょ？」と厳しく問われた（発言 16）。
- 改めて忖度なしで検証した結果、この逆転案には以下の致命的な欠陥があることが判明し、著者も「実に面白い」と納得した（発言 16〜17）：
  1. パス参照で `.` と `::` が交互に出現し（`self::field.author::required`）、書き手が定義側の括弧の種類を暗記しないとアドレスを書けない。
  2. `name(...) == name` とみなすと、`rgb(255, 0, 0)` と `rgb(0, 0, 255)` がどちらも `"rgb"` として等しくなってしまう。
  3. リストを `{ "a", "b" }` で書くことになり、Stage 1b の決定や後置 `{}`（`meta`）と正面衝突する。
  4. 著者自身が本来求めていたのは `use.0.version` のような `.` アクセスであった。
- 同時に、`( ... )` に統一したまま「値＝1 要素タプル `(value, k: v)`」として扱えば `.` アクセスだけで全て統一できる可能性が見えたが、著者が即座に**「1 個だけ弱点がある。リストの時は？」**と核心を突いた（発言 17）。

### 1.6 `(a; version: 3)` 案の検討と `@name(a; b, c)` による棄却（発言 18〜20）

- 1 要素リスト `(a)` と属性付きスカラー `(a, version: 3)` を区別するため、`:a` / `#a` / `(a;)` / `(a|)` などの区切り記号を検討し、一度は `(a; version: 3)`（セミコロンで主値と属性を分ける案）が有力に見えた（発言 18〜19）。
- しかし著者が**「`@name(a; b, c)` はどういう意味になる？」**と質問（発言 20）。
- `;` の後ろに位置引数 `b, c` が来たときの意味が定義できず（または不自然な禁止規則が必要になり）、`@name(...)` ではすでに `name` がヘッドにあるのに `(a; ...)` と書くとヘッドが二重になるという構造的破綻が露呈した。

### 1.7 リスト `list: (a, b, c)` の `...list` 参照と全通りの検証（発言 21〜23）

- 著者が「`list: (a, b, c)` とあったとき、ユーザーは `...list` を指定した時に通常 `(a, b, c)` を欲しくなる」と指摘（発言 21）。
- エージェントが一度「位置要素が 1 個の `(a, k: v)` はスカラー `a`、2 個以上の `(a, b, k: v)` はリスト `(a, b)` を返す」と提案したが、著者から**「君がどこまで本気でそう思っているかわからんな。全通り考えた？ `::use()` とか、マージ方法とか。すべて。考えて。」**と問われた（発言 22）。
- 全ケースを検証した結果、「位置要素数（1 個 vs 2 個以上）でスカラーとリストを切り替える」規則は、リストの要素が 2 個から 1 個に減った瞬間にリスト型からスカラー型へ変質してしまうこと、またマージ規則とも衝突することが判明し、完全に退けられた。
- 最終的に、矛盾が生じない 3 つの原則（無名タプルは常にタプル・属性付き値は名前付きタプル `a(version: 3)`・マージは全タプルで単一のキー再帰マージ）を整理したところで、著者の指示により本ノートに記録を残すこととなった（発言 23）。

## 2. 著者が示した原則・基準

1. **頼んでいない既存構文を勝手に変更しない（発言 3）**
   - `#(id)`（ID 接続糖衣）や `- |content`（複数行リスト項目）はそのまま維持する。
2. **`{}` は後置の `::meta(...)` 糖衣としてのみ残す（発言 6, 13）**
   - 値の位置から `{}` をなくしたため、要素・見出し・リスト項目に付く後置 `{}` は衝突なく `::meta(...)` の糖衣として機能する。
   - `{}` はあくまで `meta` フィールドであり、`version` のような構造的・必須プロパティを入れる場所として流用してはならない。
3. **宣言 `::name(...)` は `::` + 名前付きタプルであり、ヘッドにドットを繋がない（発言 6, 7）**
   - `::format.meta(...)` や `::field.author(...)` のように宣言ヘッドをドットパスにするのではなく、`::field(author: (...))` のようにタプル内部のキーとして構造化する。
   - タプル内のキーでは `url.wiki: (...)` のようなドット省略記法（`url: (wiki: (...))` と同義）を認める（発言 8）。
4. **マージ方法が異なる構造を混在させない（発言 7, 9）**
   - 同じ `::declar(...)` を複数回書いたときはマージされる。
   - ある宣言はキーマージ、別の宣言（`::use` など）はリスト連結マージ、といった**「マージ方法が違う構造」は言語の癌になるため絶対に作らない**。
   - 重複キー（同じパスのスカラー等）のマージはデフォルトでエラーとし、将来必要なら明示的な `force` の仕組みで行う。
5. **`key` に値の意味を持たせてはならない（発言 12）**
   - `key` は辿るための道筋（アドレス）であり、`::use(a: (version: 3), b: ())` のように本来「値」である `a` や `b` をキーの位置に置いてはならない。
6. **値（オブジェクト）は属性を持てる（発言 9, 17, 21）**
   - `::use(a, b, c)` の `a` や、`author: string` の `string` は、そのままでも使え、必要なら `version: 3` や `required: true` といった属性を持てるオブジェクトであるべき。
   - 同時に、`list: (a, b, c)` を `...list` で参照したときはタプル `(a, b, c)` がそのまま得られる必要がある。

## 4. 到達した地点と確認事項

発言 22 の全通り検証の末、以下の **3 つの規則** に整理された状態にある：

1. **無名タプル `( ... )` は常にタプル（コンテナ）である**
   - 要素数が 0 個 `()`、1 個 `(a)`、3 個 `(a, b, c)`、名前付き `(x: 1, y: 2)`、混在 `(a, b, sep: ",")` のいずれであっても、`( ... )` は常にタプルとして振る舞う（1 要素だからといって勝手にスカラーへ潰れない）。
   - したがって `list: (a, b, c)` や `list: (a)` に対して `...list` を参照すれば常にタプルが得られ、`list.0` で先頭要素が取れる。
2. **「属性を持つ値」は名前付きタプル `name(k: v)` で書く**
   - 属性を持たない値は `a` や `string`。
   - 属性を持たせるときは、その値をヘッドにして `a(version: 3)` や `string(required: true)` と書く。
   - これにより `::use(a(version: 3), b, c)` や `::field(author: string(required: true, default: "Anon"))` が特別構文（`::` や `;` や `{}` の流用）なしで書け、すべて `.`（`use.0.version`、`field.author.required`）で辿れる。
3. **マージ規則は全タプルで単一の「キーごとの再帰マージ」のみ**
   - タプル内のすべての要素はキー（位置要素は `"0"`, `"1"`, `"2"`…、名前付き要素は `"key"`）を持つ。
   - 2 つのタプルをマージするときは同じキー同士を再帰マージし、両方とも無名タプル `( ... )` なら再帰マージ、それ以外（スカラーや `name(...)` の衝突）はデフォルトで重複エラーとする。
   - これにより `::field(...)` や `::format(...)` は複数回に分けて書いてキーマージでき、`::use(a(version: 3), b, c)` は位置キー `"0"` が衝突するため 1 つの `::use(...)` にまとめて書くという動作が、例外ルールなしに単一の規則から導かれる。
