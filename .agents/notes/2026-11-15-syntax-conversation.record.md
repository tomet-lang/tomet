# 2026-11-15 構文の対話と、タプルの実装: 何が言われ、何が決まり、何が残ったか

逐語の記録は取っていない。これは、その日のうちに Claude が流れを追って書いたものである。
「著者が決めた」と書いたもの以外は、Claude の判定か、著者から「決めてよい」と任されて Claude が決めたものである。

## 1. 著者が決めたこと

- **タプルは決定。** `( )` は唯一の入れ物である。
- **タプルの根拠は「`{}` や `[]` が使えないから」ではない。** 著者: 「今の根拠は、`{}` と `()` の違いがわかりにくかったからという怠惰によるものだ」「名前がない object という意味にするとか」。
  到達した根拠: `( )` は頭に渡すフィールドであり、頭を書かない `( )` はその同じ物である。
- **リストは値の形として要らない。** 著者: 「プログラミング言語では、固定長と可変長の明示が必要であるが、tomet ではそれが全く必要ない。つまり、必要な形が一つ要らない」。
  「何個でも並ぶ」は場所(スキーマ)の言明である。
- **`a(version: 3)` は変。** 著者: 「`xxx()` って、`()` 内がどういう構造かが `xxx` って名前なんじゃないかな」。頭はスキーマであり、値ではない。
  11-14 の規則 2(属性を持つ値は `a(version: 3)`)はこれで退けられた。
- **`::use(vocab(a, version: 3), b, c)` はよい。** `use()` の中に入る物は vocab 型で、それをスキーマが持つ。だから頭は省略できる: `::use((a, version: 3), b, c)`。
  著者: 「そうしないと、b, c だけスカラーなのおかしいよね」。
- **`"a"` もオブジェクトである**(`string(a)`)。著者: 「これオブジェクト指向の考え方じゃないかな」。
- **`@` は構造体、`vocab(…)` はオブジェクト。** 一度「スキーマを `@` にする」(`@vocab(…)`)が出たが、著者が戻した: 「やっぱり `@` は構造体で、vocab はオブジェクトのほうがいい気がする」。
- **散文にも完全アドレス可能性が要る。** `[ ]` の中のブロックは位置で指せるべきで、そうすることで `[ ]` をリストとして扱える。id やラベルを無くす話ではない(Claude の読み違いを著者が正した)。
- **位置の項目のマージは、衝突すればエラー。**
- **JSON: 空の `()` は `{}`、あとは形で決める。**
- **`name(…)` を「名前が `Some` のオブジェクト」、`( )` を「名前が `Null` のオブジェクト」という一つの型にはしない**(著者の確認に対し、コードがそうなっていないことを確かめた)。

- **キーは値ではなく文字である。** 著者: 「全くそのとおりだと思う。ドキュメント前提の言語だからこそかな」。引用符は綴りにすぎず、`"0"` と位置 0 は同じキー。書かなかったキーも綴りの省略で、`(a, b)` と `("0": a, "1": b)` は同じ木。
  - 経緯: Claude は指示書に「キーの空間は一つ」と書き、著者に問われて「整数と文字列は別物」と取り下げ、著者の「なぜ別物なのか。明確な理由はあったか」で、理由が他言語(Python、Lua、PHP)からの借り物だったと認めて元に戻した。決め手は tomet の中の二つの規則: キーの引用符は綴り、AST は綴りを覚えない。
- **名前なしの項目のキーは、名前なしの項目を数えた番号。同じキーを二度書けばエラー**(著者: 「君の言うエラーでいいんじゃない？とりあえず」)。`("0": a, b)` はエラー。著者の最初の読みは「`b` は `"1"`」だった。
  - 「裸の整数は名前になれない」(11-13)は根拠を失った。`0: a` と書けるかどうかは未決。

## 2. 著者が出して、結論が出ていないもの

- `a@vocab(version: 3)`、`a@vocab#id(version: 3)`。Claude の判定は「間違い」(散文で `@` の働きが変わる。`@vocab(a, …)` の二つ目の綴りで新しい働きが無い)。著者は判定に答えていない。
- `#id` を宣言と参照の両方にし、どちらかは物による。`#(id)` は無くす(Claude の読み。著者の確認は無い)。
  Claude の判定: 頭に記号のある物では成り立つ。見出し、リスト項目、段落では名乗りか参照かが決まらない。
- `(a, ...)`、`(...)`、`(,)`、`(:)`。Claude の判定: 空の値が二種類になり、入れ物を一つにした決定と両立しない。著者は `(:)` について「なるほどね」と受け、JSON の既定を決める方へ進んだ。
- `name()` について著者が「問題が残っている」と言った点。何を指すのかを Claude が尋ね、答えは出ていない。
- 「`a` って何だと思う？識別子？」。Claude の答え: 外で定義された語彙を指す名前。木の上では裸の語と区別が付かず、型が言う。

## 3. Claude が決めたこと(著者: 「決めることは全部君が決めていい」)

- マージで、値が等しくても同じキーは衝突とする(Rust、Python、Swift、Dart、TOML が、同じ名前を二度書けば値が同じでもエラーにするため)。
- 見出しとリスト項目の `{ }` を、要素と同じ関数で印字する(`{ k: v }`)。以前は値として印字していて、空白が違い、ペアでない項目を落としていた。
- `{ }` どうしのマージで、要素や穴が入っていても黙って置き換えない。ペアはタプルの規則で合わせ、ペアでない項目はすべて残す。
- 型の名前は `Tuple` と `TupleEntry`。

## 4. 未決のまま残っている問い

- `x.0` と `x.name` のどちらをアドレスの正とするか(位置の項目は、スキーマでは名前も持つ)。
- `b.0 == b`(スカラーの位置 0 は自分)。頭の省略と昇格を成り立たせるために Claude が必須とした。著者は答えていない。
- 頭のない物(見出し、リスト項目、段落)の id の名乗り方。
- 段落の中(文字の並びとインラインの要素)の数え方。
- 型を書く場所(`<$…>`)。`author: string(required: true)` が崩れたので、フィールドの宣言の書き方もここに含まれる。
- `::` と `@` の関係の見直し。`string(a)` などの構築子を `$` に置くのか。
- 属性の前置か後置か(11-13 から)。
- `$` の式の空間では、`(a)` がグルーピングか一項目のタプルかという Typst と同じ問いが起きる。

## 5. 調べて分かったこと

- 他の言語がタプルを作った理由は長さではなく、「型に名前を付けずに物を組にする」こと。Rust の `(a, b)` と `Name(a, b)`、Swift と Dart の `(a, name: b)`、Typst の `arguments`、AsciiDoc の属性リスト。位置と名前が混ざる入れ物は、五つの言語すべてで「頭に渡す引数」である。
- Typst が配列と辞書を残したのは、値が変数に入って操作されるプログラミング言語だから。`[ ]` と `{ }` を内容ブロックとコードブロックに使ったので、`( )` に配列、辞書、引数、グルーピングが重なり、`(1,)` と `(:)` という跡が残った。
- 入れ物が一種類の言語(PHP、Lua、R)は、空の入れ物の JSON を書き方ではなく出力の取り決めで解いている。
- tomet に `...` の演算子は無い。11-14 の記録の `...list` は、著者の「`list` で終わるどこかのアドレス」という書き方である。
