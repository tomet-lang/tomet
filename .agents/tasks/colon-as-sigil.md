# `:` をシジルにする

**状態:** 設計未決。実装前に作者の決定が要る。

## いま `:` が何をしているか（測定済み）

`:` は開き括弧ではない。**既に埋まったスロットに、捨てずにマージする**という
修飾子。

```
@memo(a: 1)(b: 2)    → a だけ。(b: 2) は地の文に落ちる
@memo(a: 1):(b: 2)   → a と b が両方入る
@memo{a: 1}{b: 2}    → a だけ
@memo{a: 1}:{b: 2}   → a と b
```

リスト項目の中では向きの指定にもなる（`docs/spec/syntax.tmt` の「コネクト」節）。
`- @link(ref:x) :{id:breakfast}` は `{...}` を `@link` ではなく項目自身へ付ける。

`@memo:{ a: 1 }` は `@memo{ a: 1 }` と**同じ木**になる（AST 比較で確認済み）。
続ける先が無いので何もしていない。

## 非対称

```
@memo:{ a: 1 }   → 要素になる
#:{ a: 1 }       → 段落
-:{ a: 1 }       → 段落
```

`parse_heading` は `parse_groups(cur, &mut el, true)` と
`allow_colon_connect = true` で呼んでいるので**解析側は `#:` を受け入れる用意が
ある**のに、認識側 (`document.rs:109` `is_heading_start`) が `:` を知らない。
`181b542` で直した `-` と同じ食い違いが、向きを変えてもう一つ。

## 作者の見解（2026-09-08）

- `:` は別扱いすべき。
- 今 `@memo:{b: 2}` が書けるのは、おそらく `@id():` を可能にするため。
- `#:{ a: 1 }` は好ましくない。`#{a:1}` で足りる。
- **一番良いのは `:` を Sigil として扱うこと。** `@memo[content]:(b:2)` は
  `@memo` と `:` の二つの要素と考える。もともとそういう考えだった。

## `:` がシジルになると何が変わるか

`Sigil` は今 `Named(Name) | Bare | Dollar`（`crates/tomet-syntax-ast/src/lib.rs:379`）。
ここに継続を表すシジルが増える形になる。

落ちてくるもの:

- **`element.rs:49` の後続集合から `:` が消える。**「グループを開く文字」だけの
  純粋な集合になり、`sigil-follow-set.md` の切り出しが素直になる。
- **`#:{a:1}` が特例なしで弾かれる。** `:` は「直前を続ける」ものなので、`#` に
  まだグループが無ければ続ける先が無い。`is_heading_start` に `:` を足すか
  どうかという判断自体が消える。
- **`|` との対称。** `|` は行をまたいで本文を続け、`:` はグループを続ける。
  どちらも継続で、片方は行、片方はスロット。

## `:` は二つの仕事ではない。一つの規則の、位置による別解決（2026-09-08 検証）

当初「マージ」と「リスト項目への接続」の二つの機構だと書いたが、測り直したら
一つの規則だった。

> `:` は「**これは直前の要素の新しいグループではない**」という宣言。行き先は
> 位置が決める — その位置で**まだグループ枠が開いている包む構造**があれば
> それ、無ければ直前の要素の同名スロットへマージ。

| 綴り | 枠が開いた包む構造 | 行き先 | 実測 |
| --- | --- | --- | --- |
| `@memo(a:1):(b:2)` | 無し | memo の args にマージ | a と b |
| `@memo{a:1}:{b:2}` | 無し | memo の value にマージ | a と b |
| `@memo[ @id(a) :{b:2} ]` | 無し | id にマージ | id に付く |
| `- @link(x) :{id:a}` | 項目の attrs | 項目 | `<li id="a">` |
| `- @memo{a:1} :{b:2}` | 項目の attrs | 項目 | `<li data-b="2">` |

3 行目が効いている。`@memo[ ... ]` の中では `:` は外の `@memo` に届かない。
**括弧で閉じた構造は競合しない**から。リスト項目の糖衣だけが競合するのは、
閉じ括弧が無くて attrs 枠がその位置でまだ開いているため。

つまり「リストだけ特別」ではなく「枠が開いているのがリスト糖衣だけ」。
**糖衣に例外を付ける必要はない。**

いま欠けているのは規則そのもの。`allow_colon_connect` という boolean と
25 行のコメントで表現されているので二つの仕事に見える。規則として書けば
例外に見えなくなる。

### `{...}` グループの中（2026-09-08、`cf4a4a4` 後に検証）

**`:` はそこでは使えない。**両方のエントリ種別で拒否される。

```
@links{ (1)[a]{y: 2} :{z: 3} }        → ERROR
@links{ (1)[a] :{z: 3} }              → ERROR
@links{ @param(id){y: 2} :{z: 3} }    → ERROR
```

`parse_bare_element` も `parse_element` も、値グループの中では
`allow_colon_connect: false` で呼ばれるため。競合する以前に connect 形式が
提供されていない。よってこの容れ物は上の規則の反例ではなく、**規則の適用外**。

family の設計で決めること: `{...}` の中で `:` を使えるようにするか。
`@links{ (1)[a] :{z: 3} }` はエントリへのマージとして自然に読めるが、
今は書けない。

## `:as()` `:xxx()` の family と `no-vocabulary`

作者の方針: `:` は今後 `:as()` `:xxx()` のように挙動が変わるものが出てくる。
`:` 単体はその一員。

`crates/tomet-syntax-parser/.writ.tmt` の `no-vocabulary` に当たる。名前で挙動が
変わるものをパーサがマージすると、パーサが語彙を知ることになる。

上の規則がこれを解く。**行き先は位置が決め、挙動は名前が決める。**

- 行き先 — 位置だけで決まる。語彙は要らない → パーサの仕事
- 挙動 — 名前で決まる → `tomet-semantics` の仕事

前例は `normalized_element_args`。パーサは生の args を記録し、意味論が正規化した
眺めを読む側に渡す（`crates/tomet-convert-html/src/lib.rs:354` などが呼ぶ）。

## 決まったこと（2026-09-08、作者）

- **AST に stray node として残すのは不可。** content の並びに `:` 要素が混ざると、
  7 つの変換クレートが漏れなく読み飛ばす必要があり、漏れたものは黙って `:` を
  描画する。
- **`@name:`（名前の直後のコロン）は外す。ただしスコープを狭める。**
  当初の理由は「狙うスロットがまだ空なので原理的に何もできない」だったが、
  それは `:` 単体にしか当たらない。`:xxx`（機能アクセス）は空でも意味があり、
  しかも名前の直後こそ書きたい位置。

  | 綴り | 扱い |
  | --- | --- |
  | `@memo:{a: 1}` — コロン＋グループ | 外す（今も無意味） |
  | `@memo:as(x)` — コロン＋**名前** | **残す** |
  | `@memo(a:1):(b:2)` — グループの後 | 影響なし（後続集合の管轄外） |

  条件は「`:`」ではなく「`:` の直後に名前が続くとき」。`is_element_start` で
  `:` を見たあと `is_name_start_at` を確認するだけで、`eat_name` は既にある。
  → `sigil-follow-set.md` の集合から裸の `:` が消える。
- **`:[]` を今エラーにしない。** family が来れば `:` 単体はその一員で、`:[]` の
  意味は family の設計の一部になる。今エラーにすると設計より先に締め出す。
- **`:` の二つの意味**（作者、2026-09-08）:
  - `:` 単体 = **後で宣言**。名前に依存しない → パーサが解決できる（今そうしている）
  - `:xxx` = **他の要素の機能へのアクセス**。名前に依存する
- **`:xxx` の集合は閉じる。** 公式が提供するものだけで、ユーザーは `:foo` を
  定義できない。Rust のキーワードと同じ位置づけ。
- **パーサは `:name(...)` の *形* を知ってよい。** `no-vocabulary` が守っているのは
  ユーザーが拡張できる空間（`@name`）で、言語が閉じて所有する構文はその外。
  この線を writ の `no-vocabulary` の Why に追記済み。

### 形は知る、意味は知らない

Rust の字句解析器は `as` も `foo` も同じ `Ident` として出し、パーサが閉じた
テーブルと突き合わせてキーワードかを決める。マクロがその「知るのをやめる」場所で、
トークン列が入るだけでパーサは `println!` が何になるか知らない。

同じ形にする:

- パーサは `:name(...)` を一様に読み、名前は記録するだけで解釈しない
- どの名前が何をするかの表は意味論に置く

得られるもの:

1. **文法は一度しか変わらない。** メンバーを増やしても `tree-sitter-tomet` と
   全 consumer は動かない。`no-vocabulary` の二つ目の Why をそのまま満たす。
2. **`:children` が特権を持たない。** パーサから見れば `:foo` と同じ形。
3. `Element` に `connects` を足すかどうかは、この時点ではまだ決まっていない
   （下記 1 を参照）。パーサが解釈しないので、記録先だけの問題になる。

## 決まったこと（2026-09-08、その二）

- **`@memo[ a ]:[ b ]` の内容マージはしない。** `@memo| a` + `| b` が同じ木を
  作るので、二つの綴りが一つの木を指すことになる。`explicit-form-first` の
  言う重複。今の挙動のまま置く:

  ```
  @memo:[ x ]        → 段落（76bccea 以降。`:` の直後に名前が無い）
  @memo[ a ]:[ b ]   → @memo[a] と、地の文の ":[ b ]"
  ```
- **仕様 `docs/spec/builtin-elements.tmt:143-147` の `@id():` は触らない。**
  `@id` 自体がまだ定まっていないので、`:` の有無を今整理しても無駄になる。
- **`connects` の置き場所は保留。** family（`:as` など）が実装されるまで
  使い道が無い。

## 2026-09-13: `:rule` という具体例（未決定、検討中）

`@card` を実装したセッションの続きで出てきた、著者側の別要望: vocabulary の
`@element`/`@content{allow:}`（要素の**型**を宣言する側）とは別に、一つの文書
（や blueprint）の中の**特定の箇所**に「ここの中身はこれしか許さない」を
直接書きたい。案:

```tm
@section(id:"entries")[
  @card(title:"...")[ ... ]
  @heading[ これは弾かれる ]
]:rule(allow:list(card))
```

（`allow:[card]`ではなく`allow:list(card)`。下の「リストリテラルの穴」で
`[...]`は`[content]`スロットと衝突するため`list(...)`に決めた経緯を参照。）

`@section(id:"entries")[ ... ]` の時点で `(args)`/`[content]` が両方閉じている
ので、末尾の `:rule(...)` が何を食うかの曖昧さは無い。**中身は末尾の要素が
既にグループを閉じているときにだけ意味を持つ置き方**として提案された。

これは「そういうメンバーを作るかどうか」の問いに、初めて具体例で答えを迫る
ケースだと思う。`allow:[...]` という制約は args でも value でも children でも
ない第四の性質のデータで、`:as`/`:children` のように既存スロットへは
着地しない。ただし**まだ著者の決定ではない** ― 検討中。

`@content{allow:(@name)}` は素早く試すための試験的な綴りで、ほぼ無視されて
きたもの。`:rule` の設計はこれを参考にしない（片方が動くと決めてから
片方に寄せる、ではなく、別物として扱う）。

### `:rule`の検証範囲とallowの中身（2026-09-13、決定）

- **既定は子孫全部。** ルールを付けた要素の中に何段ネストしていようが、
  そこに現れる分類済みの`Element`は全部`allow`の中でなければならない。
  地の文（プレーンテキスト・段落）は対象外――あくまで要素の種類だけを見る。
- **`direct:@bool`で直下の子だけに絞れる**（既定`false`=子孫全部、
  `true`=直下のみ）。既存の`@bool`フラグの作法
  （`required:`/`positional:`/`singleton:`）に合わせる:
  `:rule(allow:list(card), direct:true)`。
- **`allow`にはカスタム名前空間の名前も書ける**
  （`allow:list(card, ns.mycard)`）。これが実装上の制約を生む:
  `classify_std_lenient`は`std`しか知らないので`ns.mycard`が本当に
  宣言された名前かどうか判定できない。文書が`@use`で持ち込んだ語彙まで
  解決する`Bindings::classify`（`tomet-semantics::vocabulary`）が要る。
  → **`:rule`の検証は文書全体の語彙解決が終わった後にしか動かせない**、
  という順序の制約が一つ生まれる。

### 副産物: リストリテラルの穴（未決定）

`allow:` の値をどう書くかで、Tomet 全体に効く別の穴が出てきた。`[...]` は
`[content]` スロット（複数行にまたがる本文）の意味を既に持っていて、他の
言語の「`[]` はリスト」という直感と衝突する。三案が出た:

1. Typst 式に `()` を配列にする。→ 却下寄り。`(...)` は既に args
   グループという重い意味を持っており、意味の付け替え先を変えるだけで
   問題は解決しない。
2. `list(...)` / `enum(...)` という明示のコンストラクタ関数を作り、裸の
   `(...)` はその糖衣として**後で**考える。→ 今のところこれで検討を
   進める。`explicit-form-first` にそのまま乗る（`list(...)` が明示形、
   裸 `()` は展開される糖衣）。新しい記号を増やさず、`[]` の意味も
   汚さない。
3. `(args)` の中でだけ `[]` をリストにする。→ 却下寄り。文書の流れと
   無関係な位置依存の書き分けを読者に覚えさせることになる。

**現状の結論（暫定）:** 案2で進める。糖衣（裸 `()`）は今は決めない。
`list(...)`/`enum(...)` という値が `_entry_value` にまだ形を持たない
（`@content` の `(link, em)` が読めないのと同じ理由）ので、これも
グラマー側の新規実装が要る。

#### `list()`/`enum()` の文法（2026-09-13、決定）

`value.rs:396`の`parse_entry_value`（と`parse_value_shape`共有部）は今
`[`→seq、`"`→quoted、`{`→map、それ以外→`eat_scalar_raw`の4分岐。
`eat_scalar_raw`は`(`/`[`/`{`を深さだけ数えて素通りするので、
`key:list(card)`は今丸ごと生文字列`"list(card)"`に飲み込まれる
（`@content`の`(link, em)`と同じ理由）。

- `eat_scalar_raw`にフォールバックする**前**に分岐を一個足す:
  「識別子(`is_name_start_at`/`eat_name`、`@name`/`:name`と共通)の直後に
  `(`が続く」を検知したら呼び出しとして読む。
- 中身は`,`区切りで`parse_entry_value`を再帰適用。ネストした
  `list(...)`や`{...}`もこれで自然に書ける。
- 新しい `Value::Call(String, Vec<Value>)`。**引数は位置指定のみ**
  ―`key:value`混在（名前付き引数）は無し。リストである以上、
  順序付きの値の並びで十分。
- 名前は一切見ない。`list`だろうが`enum`だろうがタイポの`lst`だろうが
  同じ形で受理する ― `:xxx`と同じ「パーサは形だけ、意味は意味論」。
  `list`/`enum`が実在する名前だという閉じた表を持つのは`tomet-semantics`
  だけ（要素名・コネクト名に続く3つ目の閉じた集合）。

`${func(args)}`側の`InterpExprKind::Call{callee, args}`
(`tomet-syntax-ast/src/lib.rs:637`)とは**意図的に別物**。同じ
`name(args)`という見た目を共有するだけで、`${...}`は後で評価される式、
`list(...)`は今すぐ確定するリテラル。混ぜると「評価されるかどうか」が
読み手に伝わらなくなる。

### 実装に向けて分かったこと（検証済み）

`:name(...)` は **まだ何も実装されていない**。`element.rs` の
`is_element_start` は `:` の直後に名前があるかだけ確認して「要素として
成立する」と判定するが、`parse_groups` 側には `:name(...)` を消費する分岐が
無い ― 現状のコネクト分岐（`allow_colon_connect && cur.eat_str(":")`直後）は
`(`/`{` の裸グループしか見ておらず、名前が続く場合は丸ごとロールバックされて
地の文に落ちる。つまり `:rule` は「既存の分岐に一個足す」規模ではなく、
family 全体の初回実装になる。

### パーサ/意味論の境界（2026-09-13、決定）

「行き先は位置が決める（パーサ）、挙動は名前が決める（意味論）」
（前例 `normalized_element_args`）をそのまま押し通す形で決めた。

- **パーサ**: `:`の直後に名前があれば、`@name`と同じ`parse_groups`を
  再利用してargs/content/valueを読む。名前が`rule`だろうがタイポの`rul`
  だろうが区別しない（`@name`がどんな名前でも構文的に受理されるのと同じ）。
  結果は`Element`の専用フィールドに積む。名前の妥当性は一切見ない。
- **意味論**: `rule`/`as`/`children`...の閉じた表を持つのは
  `tomet-semantics`だけ（`BUILTIN_KINDS`と同じ形の別テーブル、要素名とは
  別の名前空間）。各名前の意味・正規化もここ。表に無い名前は
  パースエラーではなく検証診断（`UnknownName`と同じ立ち位置、別の集合）。

### 複数コネクトを重ねられるようにする（2026-09-13、決定）

`@x(...):as(y):rule(...)`のように**複数のコネクトを重ねられる**ように
設計する。よって専用フィールドは `Option<Box<Element>>` ではなく
**`Element::connects: Vec<Element>`**（空Vecで「無し」、`Document.blocks:
Vec<Block>`と同じ流儀）。

上の「要るとしたら`Vec<Element>`を専用フィールドに」（2026-09-08）は
*一つのコネクトの中身*（`:children[a,b,c]`のような）の話で、これとは別の
Vec。混同しないこと。

パーサ側の変更は小さい: `parse_groups`は元々loopで毎周回グループを探す
構造なので、「見つけたら1個で確定」を「見つけたらVecにpushしてloop継続」に
変えるだけで乗る。

**保留（2026-09-13）:** 同じ名前を二重に重ねたとき（`:rule(...):rule(...)`
`:as(x):as(y)`）の意味論——パーサはVecに両方積むだけで構わないが、それを
名前ごとに「複数あってよい」とするか「エラー」とするかは、`:xxx`の
メンバーが今2〜3個の仮説段階では決めるには材料が足りない。メンバーが
揃ってから判断する。
