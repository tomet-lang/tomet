# `:` をシジルにする

**状態:** 設計未決。実装前に作者の決定が要る。

## いま `:` が何をしているか（測定済み）

`:` は開き括弧ではない。**既に埋まったスロットに、捨てずにマージする**という
修飾子。

```
@memo(a: 1)(b: 2)    → a だけ。(b: 2) は地の文に落ちる
@memo(a: 1):(b: 2)   → a と b が両方入る
@memo{a: 1}{b: 2}    → a だけ
@memo{a: 1}:{b: 2}   → a と b
```

リスト項目の中では向きの指定にもなる（`docs/spec/syntax.tmt` の「コネクト」節）。
`- @link(ref:x) :{id:breakfast}` は `{...}` を `@link` ではなく項目自身へ付ける。

`@memo:{ a: 1 }` は `@memo{ a: 1 }` と**同じ木**になる（AST 比較で確認済み）。
続ける先が無いので何もしていない。

## 非対称

```
@memo:{ a: 1 }   → 要素になる
#:{ a: 1 }       → 段落
-:{ a: 1 }       → 段落
```

`parse_heading` は `parse_groups(cur, &mut el, true)` と
`allow_colon_connect = true` で呼んでいるので**解析側は `#:` を受け入れる用意が
ある**のに、認識側 (`document.rs:109` `is_heading_start`) が `:` を知らない。
`181b542` で直した `-` と同じ食い違いが、向きを変えてもう一つ。

## 作者の見解（2026-09-08）

- `:` は別扱いすべき。
- 今 `@memo:{b: 2}` が書けるのは、おそらく `@id():` を可能にするため。
- `#:{ a: 1 }` は好ましくない。`#{a:1}` で足りる。
- **一番良いのは `:` を Sigil として扱うこと。** `@memo[content]:(b:2)` は
  `@memo` と `:` の二つの要素と考える。もともとそういう考えだった。

## `:` がシジルになると何が変わるか

`Sigil` は今 `Named(Name) | Bare | Dollar`（`crates/tomet-syntax-ast/src/lib.rs:379`）。
ここに継続を表すシジルが増える形になる。

落ちてくるもの:

- **`element.rs:49` の後続集合から `:` が消える。**「グループを開く文字」だけの
  純粋な集合になり、`sigil-follow-set.md` の切り出しが素直になる。
- **`#:{a:1}` が特例なしで弾かれる。** `:` は「直前を続ける」ものなので、`#` に
  まだグループが無ければ続ける先が無い。`is_heading_start` に `:` を足すか
  どうかという判断自体が消える。
- **`|` との対称。** `|` は行をまたいで本文を続け、`:` はグループを続ける。
  どちらも継続で、片方は行、片方はスロット。

## `:` は二つの仕事ではない。一つの規則の、位置による別解決（2026-09-08 検証）

当初「マージ」と「リスト項目への接続」の二つの機構だと書いたが、測り直したら
一つの規則だった。

> `:` は「**これは直前の要素の新しいグループではない**」という宣言。行き先は
> 位置が決める — その位置で**まだグループ枠が開いている包む構造**があれば
> それ、無ければ直前の要素の同名スロットへマージ。

| 綴り | 枠が開いた包む構造 | 行き先 | 実測 |
| --- | --- | --- | --- |
| `@memo(a:1):(b:2)` | 無し | memo の args にマージ | a と b |
| `@memo{a:1}:{b:2}` | 無し | memo の value にマージ | a と b |
| `@memo[ @id(a) :{b:2} ]` | 無し | id にマージ | id に付く |
| `- @link(x) :{id:a}` | 項目の attrs | 項目 | `<li id="a">` |
| `- @memo{a:1} :{b:2}` | 項目の attrs | 項目 | `<li data-b="2">` |

3 行目が効いている。`@memo[ ... ]` の中では `:` は外の `@memo` に届かない。
**括弧で閉じた構造は競合しない**から。リスト項目の糖衣だけが競合するのは、
閉じ括弧が無くて attrs 枠がその位置でまだ開いているため。

つまり「リストだけ特別」ではなく「枠が開いているのがリスト糖衣だけ」。
**糖衣に例外を付ける必要はない。**

いま欠けているのは規則そのもの。`allow_colon_connect` という boolean と
25 行のコメントで表現されているので二つの仕事に見える。規則として書けば
例外に見えなくなる。

### `{...}` グループの中（2026-09-08、`cf4a4a4` 後に検証）

**`:` はそこでは使えない。**両方のエントリ種別で拒否される。

```
@links{ (1)[a]{y: 2} :{z: 3} }        → ERROR
@links{ (1)[a] :{z: 3} }              → ERROR
@links{ @param(id){y: 2} :{z: 3} }    → ERROR
```

`parse_bare_element` も `parse_element` も、値グループの中では
`allow_colon_connect: false` で呼ばれるため。競合する以前に connect 形式が
提供されていない。よってこの容れ物は上の規則の反例ではなく、**規則の適用外**。

family の設計で決めること: `{...}` の中で `:` を使えるようにするか。
`@links{ (1)[a] :{z: 3} }` はエントリへのマージとして自然に読めるが、
今は書けない。

## `:as()` `:xxx()` の family と `no-vocabulary`

作者の方針: `:` は今後 `:as()` `:xxx()` のように挙動が変わるものが出てくる。
`:` 単体はその一員。

`crates/tomet-syntax-parser/.writ.tmt` の `no-vocabulary` に当たる。名前で挙動が
変わるものをパーサがマージすると、パーサが語彙を知ることになる。

上の規則がこれを解く。**行き先は位置が決め、挙動は名前が決める。**

- 行き先 — 位置だけで決まる。語彙は要らない → パーサの仕事
- 挙動 — 名前で決まる → `tomet-semantics` の仕事

前例は `normalized_element_args`。パーサは生の args を記録し、意味論が正規化した
眺めを読む側に渡す（`crates/tomet-convert-html/src/lib.rs:354` などが呼ぶ）。

## 決まったこと（2026-09-08、作者）

- **AST に stray node として残すのは不可。** content の並びに `:` 要素が混ざると、
  7 つの変換クレートが漏れなく読み飛ばす必要があり、漏れたものは黙って `:` を
  描画する。
- **`@name:`（名前の直後のコロン）は外す。ただしスコープを狭める。**
  当初の理由は「狙うスロットがまだ空なので原理的に何もできない」だったが、
  それは `:` 単体にしか当たらない。`:xxx`（機能アクセス）は空でも意味があり、
  しかも名前の直後こそ書きたい位置。

  | 綴り | 扱い |
  | --- | --- |
  | `@memo:{a: 1}` — コロン＋グループ | 外す（今も無意味） |
  | `@memo:as(x)` — コロン＋**名前** | **残す** |
  | `@memo(a:1):(b:2)` — グループの後 | 影響なし（後続集合の管轄外） |

  条件は「`:`」ではなく「`:` の直後に名前が続くとき」。`is_element_start` で
  `:` を見たあと `is_name_start_at` を確認するだけで、`eat_name` は既にある。
  → `sigil-follow-set.md` の集合から裸の `:` が消える。
- **`:[]` を今エラーにしない。** family が来れば `:` 単体はその一員で、`:[]` の
  意味は family の設計の一部になる。今エラーにすると設計より先に締め出す。
- **`:` の二つの意味**（作者、2026-09-08）:
  - `:` 単体 = **後で宣言**。名前に依存しない → パーサが解決できる（今そうしている）
  - `:xxx` = **他の要素の機能へのアクセス**。名前に依存する
- **`:xxx` の集合は閉じる。** 公式が提供するものだけで、ユーザーは `:foo` を
  定義できない。Rust のキーワードと同じ位置づけ。
- **パーサは `:name(...)` の *形* を知ってよい。** `no-vocabulary` が守っているのは
  ユーザーが拡張できる空間（`@name`）で、言語が閉じて所有する構文はその外。
  この線を writ の `no-vocabulary` の Why に追記済み。

### 形は知る、意味は知らない

Rust の字句解析器は `as` も `foo` も同じ `Ident` として出し、パーサが閉じた
テーブルと突き合わせてキーワードかを決める。マクロがその「知るのをやめる」場所で、
トークン列が入るだけでパーサは `println!` が何になるか知らない。

同じ形にする:

- パーサは `:name(...)` を一様に読み、名前は記録するだけで解釈しない
- どの名前が何をするかの表は意味論に置く

得られるもの:

1. **文法は一度しか変わらない。** メンバーを増やしても `tree-sitter-tomet` と
   全 consumer は動かない。`no-vocabulary` の二つ目の Why をそのまま満たす。
2. **`:children` が特権を持たない。** パーサから見れば `:foo` と同じ形。
3. `Element` に `connects` を足すかどうかは、この時点ではまだ決まっていない
   （下記 1 を参照）。パーサが解釈しないので、記録先だけの問題になる。

## まだ決まっていないこと

**1. どこに掛けるか。** stray node は不可だが、family には名前と groups を
記録する場所が要る。パーサは名前を解釈しないと決まったので、これは純粋に
「どこに置くか」だけの問題になった。候補は**受け取る側のスロット**:

```rust
pub struct Element {
    ...
    pub connects: Vec<Connect>,   // 名前・groups・それだけ
}
```

content を歩く変換クレートは `:` に出会わない。パーサは名前を解釈せず記録する
だけなので `no-vocabulary` も通る。裸の `:` は名前に依存しないマージなので、
パーサが今までどおり畳んでしまってもよい。

`Element` に 4 つ目のフィールドを足すのは小さくない。他の形があれば比較する。

（以前あった「`:as` は args キーか機能アクセスか」という問いは、この決定で
消えた。パーサは形だけを読み、`:as(x)` が args に `as: x` を置くことは意味論の
テーブルの一項目になる。args キーか機能かという区別自体が要らない。）

**2. `:[]` の `:` を飲むか残すか。** 今は**黙って飲まれる**。

```
@memo:[ x ]        → 内容 x。`:` は消える
@memo[ a ]:[ b ]   → `:[ b ]` が地の文に落ちる
```

エラーにしないのは決定済みだが、飲んで捨てるか、飲まずに残すかは別。family が
来たとき `:as[ x ]` の `as` が消えるのは困るはず。

**3. `@id():` の扱い。** 仕様 `docs/spec/builtin-elements.tmt:143-147` の 4 例を
`:` 無しと AST 比較したところ、3 例が**同一**だった。

| 綴り | `:` 無しと |
| --- | --- |
| `@id(a):()` | `@id(a)` と同一 |
| `@id(a):[]` | `@id(a)[]` と同一 |
| `@id(a):{tag: x}` | `@id(a){tag: x}` と同一 |
| `@id(a):(){}[]` | 差あり（`:` 無しだと 2 つ目の `()` が重複で落ちるため） |

一般則: **`:` は狙ったスロットが既に埋まっているときにしか効かない。**
仕様のこの節は `:` 無しで書き直せる。書き直すかは規範層の話なので作者の決定。
