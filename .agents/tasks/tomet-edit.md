# tomet-edit: backend-neutral editable model for collaborative editing

Goal: a CRDT-agnostic, editable tree model of a Tomet document so that apps
can bridge it to a CRDT (Loro, Yjs, ...) for real-time collaboration. The CRDT
adapters live in the apps, not in this repo.

Status (2026-09-26): crate skeleton exists and builds; no model code yet. The
next step is the model types, once the paragraph question below is confirmed.

## Decisions (agreed with the author)

- Crate: `crates/tomet-edit`, package `tomet-edit`. Layer 4, listed by name in
  the root `.writ.tmt` `crate-layering` rule (same treatment as `serde_tomet`,
  `tomet-extract`, `tomet-search`). May depend on `tomet-tree`.
- No dependency on any CRDT library. No sync/session/transport code.
- Basis is the CST (`tomet-cst`, built by `tomet_parser::parse_cst`). It was
  shallow at first and was since rebuilt: sections nest by level, elements and
  their `( )` `{ }` `[ ]` groups and map/seq entries are structured nodes,
  comments stay in place as `COMMENT` tokens, and `parse_cst(src).text() == src`
  holds. Still flat: emphasis `*em*`, `|` runs, plain list-item content.
- Node granularity: `Section`, block `Element` (incl. list items), `Paragraph`
  are tree nodes; `{}` data is map/seq (key-level merge); CST tokens are not
  nodes.
- Layout trivia and comments are kept per node and written back as they were,
  not regenerated by the formatter. The formatter prints only nodes that were
  created or edited.
- Edit operations are a small closed set of values: insert, delete, move,
  set attribute, edit text. `move` is first-class; a backend without native
  move degrades to delete+insert.
- Import/export: `source -> model` and `model -> source`. Invariant: import
  followed by export with no edits is byte-identical.
- Diagnostics: after edits, export the source, re-parse it with the real
  parser (`parse_document`) and run the validator (duplicate `unique`, dangling
  `^id`). The CST may disagree with the AST parser where it "prefers the
  reading that keeps more structure", so diagnostics must not run on the model.
  A CRDT cannot reject writes, so this only reports.
- Every node gets an opaque id at import; the app maps it to its own node ids.
- One model per file. Cross-file references are plain values.
- Library facts checked (2026-09-26): Loro has a movable tree (fractional-index
  child order, per-node `LoroMap`), movable list and rich text; Automerge has
  map/list/text with Peritext marks (scalar values only) and no documented
  move; Yjs has no move, to be verified from a primary source.

## Recommended, awaiting the author's confirmation

Paragraph, heading and element-content text is held as the original source
text (one text value), not as marks over `Inline::Element`. Reasons: structure
in the model is worth it where there is identity, move or a key (sections,
blocks, `{}` data), not inside prose; round-trip identity is then trivial;
emphasis is flat in the CST anyway, so marks would be a half-structure; and it
avoids depending on whether Loro marks can carry structured values. Cost: two
people can concurrently break brackets of one inline element; the CST is
resilient and the post-edit diagnostics report it. If confirmed, this also
closes the old open items about `SoftBreak` / `LineBreak` / `Raw` and Loro
marks (they are plain characters of the text).
