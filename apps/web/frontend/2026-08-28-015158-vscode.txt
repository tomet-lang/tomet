● crates/typedmark-syntax-parser/src/embedded_format.rs:1-8
  のコメント通り、@meta(format:yaml){...} のような format:yaml 指定要素の {...}
  中身は typedmark の構文を一切介さず、生の YAML テキストとして serde_yaml 
  にそのまま渡される、という仕様です（{} の対応と文字列リテラルの中だけ見て、中
  身自体は不透明として扱う、と明記されています）。

  なのでエラーメッセージは typedmark 側のバグではなく、素直に YAML パーサが
  @link(ref:$2026-08-26) を YAML として読めていない、というだけです。原因は
  @。YAML の仕様上 @（と `）は「将来の予約用」の indicator
  文字で、**クォートなしの plain scalar の先頭には使えません**。8行目の値が
  @link(...) のような文字列で始まっていて、クォートされていないためスキャナがそ
  こで詰まっています。

  正解は、その値をクォートで囲むことです：

  foo: "@link(ref:$2026-08-26)"

  （もしくはブロックスカラー |/>
  で書く手もありますが、単発の値ならダブルクォートで十分です。）

  要は「format:yaml ブロックの中は typedmark ではなく素の YAML
  なので、YAML的に特殊な文字（@ ` : - # など）で始まる値は普通の YAML
  と同じルールでクォートが必要」という話です。typedmark 側の @link(...)
  記法をそのまま YAML
  の値としてノークォートで書けるわけではない、という点だけ意識すれば大丈夫です。

     edit
     typedmark-web: editor experience + feedback quality upgrade

     Context

     apps/web (typedmark-web) is a small Axum server that serves a static
     playground (apps/web/static/{index.html,style.css,app.js}) with two
     JSON endpoints (/api/parse, /api/format) backed directly by
     typedmark-parser/typedmark-formatter/typedmark-html/
     typedmark-markdown. Today the editor is a plain <textarea> — no
     syntax highlighting, no line numbers — and parse errors surface as one
     line of status text plus a browser title hover tooltip holding a
     rustc-style snippet the server already generates
     (format_parse_error in apps/web/src/main.rs). The user wants this
     made much more pleasant to actually work in.

     Scope for this pass, per direct confirmation: editor experience and
     feedback quality. Save/share links, file load, a format diff view,
     and in-browser LSP (hover/completion) are explicitly deferred — not
     touched here. UI changes are scoped to what's needed to integrate the
     new editor cleanly (matching the existing dark theme's CSS variables),
     not a broader redesign.

     Also confirmed: a real JS build pipeline is wanted (not a CDN import,
     not a vendored single-file library) — mirroring the pattern this repo
     already uses for the VS Code extension.

     Approach

     Editor: CodeMirror 6, hand-written StreamLanguage highlighter

     CodeMirror 6 (not Monaco — much lighter, no web-worker setup needed,
     better fit for a playground this size) replaces the <textarea>. For
     TypedMark syntax highlighting, write a StreamLanguage-based tokenizer
     (@codemirror/language's StreamLanguage.define(...)) rather than a
     full Lezer grammar or a WASM build of tree-sitter-typedmark — both of
     those are a much bigger lift (a Lezer grammar is comparable effort to
     writing tree-sitter's grammar.js from scratch; a WASM tree-sitter build
     needs an Emscripten toolchain in the nix build) than this pass calls
     for. Port the token categories from the existing TextMate grammar
     (editors/vscode/syntaxes/typedmark.tmLanguage.json) as the reference
     for what to recognize: headings (#[...]), @name/<T> elements and
     their (args)[content]{value} groups, comments (//, /* */),
     emphasis/strong/mark, code spans, list markers, thematic breaks.
     Theme the editor via EditorView.theme(...) using the same CSS
     custom properties already in style.css (--bg-input, --text-main,
     --accent, etc.) so it matches the existing dark theme automatically
     rather than needing a second, hand-synced palette.

     Feedback quality: @codemirror/lint + a persistent problems area

     - Wire /api/parse's existing line/column/message error fields
     into a CodeMirror linter() (@codemirror/lint), converting to a
     document offset so the error renders as an inline squiggly underline
     at the exact offending position, plus a gutter marker and a hover
     tooltip — a real upgrade from today's one-line status text. The
     parser is recursive-descent (stops at the first error), so this will
     only ever surface one diagnostic at a time; that's an existing
     backend property, not something this pass changes.
     - Replace the current hover-only title attribute with an always-
     visible panel that shows the server's rustc-style snippet
     (format_parse_error's output, already returned as
     error.formatted) whenever there's a parse error, instead of
     requiring the user to hover to see it.
     - Format action: after applying /api/format's result, restore the
     cursor to roughly the same line/column (clamped to the new line's
     length) instead of resetting it to the start — small, but a real
     "editor experience" paper cut today since format currently does a
     blind full-content replace.
