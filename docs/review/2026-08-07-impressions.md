# examples/typedmark.tmt を読んだ感想 (2026-08-07)

`examples/typedmark.tmt` および README 系ファイルを見ての所感。

## 良いと思った点

- `<T>(input)[area]{value}` という「型付きインライン要素」を単一の統一記法で表そうとしている発想が筋が通っている。リンクも画像もinputも同じ形に落とし込める。名前の "Typed" はここから来ていそう。
- `@links { (1)[...] (anotation1)[...] }` + `@link(ref:anotation1)` の、注釈を後方で定義して前方から参照する形は、Markdownの参照リンク(`[text][ref]`)の発展形として自然。
- `##[...]\n{ id: header1.2 }` のように見出し本文と属性ブロックを改行して分離できるのは、Pandocの`{#id .class}`より柔軟そう（複数行見出しに対応しやすい）。

## 気になった点・引っかかった点

1. **`examples/typedmark.tmt` は「例」というより「設計メモ」になっている。**
   ファイル自体に `(?)[ こっちのほうがいいか？ ]` や「リンクのフォーマットがまだ完全に決まっていない」「新たな名前がほしい」という迷いがそのまま書かれている。パーサーのテストケースやドキュメントのサンプルとしてこのファイルを使うなら、確定した記法だけの版と、検討中メモ版は分けたほうが後々事故りにくい。

2. **`[]` の衝突問題は本質的。**
   作者自身が指摘の通り、`[ ]` を「ネスト」「area」「リストの一部？」で使い回そうとしていて、リストの `-` 記法と行頭で衝突しうる。`""` を代替にという案も出ているが、`"..."` は文字列リテラルの見た目になるため「エリア（ラベル的な意味）」を表すには直感的でない可能性がある。`{}` を属性、`[]` を常にネスト/エリア専用にし、リスト記号を `-` 以外にする方が衝突を避けやすいかもしれない。

3. **`@link(ref:...)` と `[Wiki](url:...)` の二重記法。**
   同じ「リンク」なのに `@link(...)` 形式と Markdown 由来の `[text](url:...)` 形式が両方出てきていて、統一記法を目指す言語としては一貫性が崩れている。本文中でも「まだ完全に決まっていない」と自覚されている箇所。

4. **インフラ先行気味。**
   tree-sitter文法、lexer/parser/ast/formatter/lsp/validator/renderer に加え Java/JS/Rust/VSCode/Zed 向けラッパーまで、かなり本格的なツールチェーンがすでに用意されている一方、肝心の構文（特にリンクとネストの記法）がサンプル内でまだ「問題」として明記された未確定状態。コア構文をもう少し固めてからツール群を広げる方が手戻りが少なそう。

## まとめ

統一記法というコンセプトは筋が良いが、`[]` の多義性とリンク記法の二重化がまだ未解決で、それを解く前にツールチェーンの方が先行している、という印象。
